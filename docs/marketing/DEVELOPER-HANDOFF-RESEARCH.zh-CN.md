# UIDelta ZIP：给前端的价值与宣传依据

调研日期：2026-09-04。方法：公开一手资料研究 + UIDelta 已发布导出代码核对。没有开展开发者访谈、计时对照或 Codex 成功率实验。

## 结论

**ZIP 交付是值得突出的产品亮点：把页面上的视觉反馈，变成前端和编码 Agent 可以继续处理的上下文。**

按一次视觉问题的交接流程，可以归纳出 **6 类受到帮助的痛点**。这个数量是产品分析的分类，不是用户调查结果，也不表示已经自动解决了整个修复过程。

效率价值主要发生在真正改代码之前：少找页面和元素、少追问目标值、少手工组织 AI 输入。具体能节省多少分钟、提升多少百分比，需要实测。

## 六类痛点，ZIP 提供了什么

| 开发者接手时的问题 | 包内可用信息 | 可以减少的重复工作 | 仍需要什么 |
| --- | --- | --- | --- |
| 1. 这是哪个页面？ | 页面 URL、路由、标题 | 从聊天记录里追问链接、寻找目标页面 | 可访问的环境、登录态；测试域名到本地环境的映射 |
| 2. 是哪个同名按钮或卡片？ | 首选 / 回退 DOM 选择器、test id、文本、父级信息 | 对着截图反复点选、辨认元素 | 在当前页面验证唯一匹配，再查源码实现 |
| 3. 当时为什么看起来不一样？ | 视口、滚动位置、记录时间、页面全景与元素细节 | 重新收集截图、确认窗口尺寸和局部位置 | 登录条件、交互步骤、动态数据等未被自动记录的状态 |
| 4. 到底差多少、要改成什么？ | 实测尺寸、样式、间距；问题描述；存在时的设计差异 / 参考图 | 再量一次已记录的数值、重复澄清视觉目标 | 明确的期望值或参考依据；工具不会凭空知道设计意图 |
| 5. 还要给 AI 重写一遍吗？ | `report.md`、`issues.json`、`assets/` 及附件关联 | 手工粘贴选择器、转述截图、拼装多份上下文 | Codex 可读取的项目目录、运行环境与修改权限 |
| 6. 改完怎么逐条交代？ | 问题编号、描述、优先级及对应截图 | 重新建立问题和修改结果之间的对应关系 | 运行检查、按编号复核；ZIP 不自动回写处理状态 |

字段按记录模式和页面情况而异：没有 `data-testid` 的页面不会凭空产生 test id，框选区域也不保证存在唯一 DOM 元素。

## 三个适合对外宣传的收益

**少找一遍。** 页面地址和元素定位随问题交付。前端与 Codex 有明确的查找起点。

**少猜一轮。** 实测值、截图和修改要求放在一起。像「实际 24px，请改为 16px」这样的要求可以直接用于修改和复核。

**少拼一次上下文。** 将 ZIP 放进项目，告诉 Codex 文件路径，让它读取已有材料、查找对应实现并按要求修改。

推荐主标题：**让 Codex，接着改。**

推荐辅助文案：**网页地址、元素定位、截图和修改要求，打包交给项目里的 Codex。**

## 为什么这个方向有依据

### Bug 报告需要可复现的事实

Mozilla 的缺陷报告指南要求给出清楚的复现步骤、实际结果与期望结果，并区分观察和猜测。这说明「只有一句不对」通常不足以支持开发处理。UIDelta 补齐的是页面、视觉证据与定位材料；交互复现步骤仍需记录者补充。[Mozilla Bug Writing Guidelines](https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html)

### Codex 需要目标、上下文和验证方式

OpenAI Docs 的 Codex 提示指南建议说明要实现的行为、相关代码或复现步骤、约束及验证方式；CLI 可在本地仓库读取文件、编辑代码与运行工具。由此推断，把现有报告文件作为输入，比要求前端重新转述全部网页信息更适合这个工作流。[Codex 提示指南](https://learn.chatgpt.com/docs/prompting#prompting-codex)、[Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

这两份文档支持工作流的可行性，没有证明 UIDelta 的实际提效比例或修复成功率。这里也没有把「所有 Codex 客户端都能直接拖入 ZIP」当成已验证事实；通用方式是给出可读取的本地 ZIP 或解压目录路径。

### 元素定位要有多条线索

Playwright 文档推荐使用用户可见属性或 test id 等明确约定，并指出与 DOM 结构绑定的长 CSS / XPath 链可能随页面变化失效。因此 UIDelta 的选择器应与文本、test id、截图相互核对，而不是被宣传为永久不变的源码地址。[Playwright Locators](https://playwright.dev/docs/locators)

### 竞品也在解决技术信息丢失

BugHerd 官方说明会随反馈采集截图、浏览器、操作系统和 CSS 选择器，并进入其任务看板。这证明带技术上下文的视觉反馈是一条已有产品路径；「能记录 CSS 选择器」本身不是独有能力。[BugHerd 官方功能说明](https://bugherd.com/visual-design-feedback-tool)

UIDelta 更适合强调自身组合：**开源、本地保存、文件交付、Markdown + JSON + 图片可供项目里的 Agent 读取**。本次没有逐一验证竞品的全部导出能力，不作「唯一」或排他性比较。

## 一个贴近前端工作的例子

宣传示例中，`[data-testid='brand-project']` 指向卡片，但卡片之间的 `gap` 来自父容器 `.projects`。Codex 需要沿元素线索查找并确认样式来源，再把 24px 改为明确要求的 16px。仅把选择器直接拼进一条覆盖样式，并不能保证修对。

这是源码可核对的流程示意，图中的修改与验收目标不代表已经完成一次独立、盲测的 Codex 修复实验。

## 下一步怎么验证提效

用实际间距、字号、颜色、响应式布局等问题做配对对照：一组用原有截图与文字，另一组用 UIDelta ZIP。保持项目、Agent 配置和验收标准一致，并交换任务顺序以减小熟悉度影响。

记录四项：从收到反馈到首次定位正确实现的时间、追问次数、到通过复核的总用时、错误修改与返工情况。单独记录测量与导出所需时间，避免把成本从前端转移给设计师后仍声称整体提效。

在得到这些数据前，公开文案使用「减少重复定位和上下文整理」，不使用「效率提升 X%」「一键精准修复所有问题」或虚构用户证言。
